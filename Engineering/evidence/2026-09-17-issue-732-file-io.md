# Issue #732: Windows file I/O investigation

## Scope and risk

Risk **R3**: file-handle lifecycle, ordering, cancellation, persistent contents,
and compatibility. This work investigates
[issue #732](https://github.com/WebFirstLanguage/wfl/issues/732) on current main
`c60a66e3dab028d0eb8fd0d2f56c37b1d600b803`, rather than assuming the historical
`db11db97` results still describe the integrated code.

Environment: Windows x86-64, Rust 1.98.1 (`48a229cea`, 2026-09-01), Cargo 1.98.1
(`797e8a9bc`, 2026-08-05), 32 logical CPUs, default Rust test concurrency.
The main checkout was clean before investigation. A detached baseline worktree
and separate baseline/fix Cargo output directories retain revision isolation.
Raw logs are under `target/reports/issue-732/`; they are not tracked.

## Baseline and storage measurements

`cargo test --locked --test file_io_concurrent_test
--test file_io_error_handling_test --test file_io_performance_test --no-fail-fast`
on the unchanged main revision produced:

| Target | Passed | Failed | Observed failures |
| --- | ---: | ---: | --- |
| Concurrent | 7 | 0 | None |
| Error handling | 6 | 4 | Closed-handle use, read-only-file case, nested error handling, same-file access: `Operation timed out` |
| Performance | 7 | 0 | None; entire target completed in 0.07 seconds |

After `cargo build --release --locked`, the clean detached baseline worktree's
`cargo test --all --locked --no-fail-fast` completed with **2,240 passed,
4 failed, 27 existing ignored**, exit 101. The only failing target was error
handling: closed-handle use, nested error handling, double close, and same-file
access all timed out. The concurrent and performance targets each passed 7/7.
The changing failed-case subset is consistent with shared storage latency;
passing isolated cases do not erase the recorded full-run failures.

PR #727 already moved the concurrent and performance fixtures to independent OS
temporary directories. Their time limits remained unchanged. The error-handling
suite still wrote to the checkout directory, used shared literal filenames, and
cleaned them only after successful assertions. Its catch-all WFL programs also
accepted both success and error, masking incorrect behavior.

A separate diagnostic wrote one byte to each of five distinct files on each
volume, timing only `.NET FileStream.Flush(true)` (a real disk synchronization),
then closing and deleting each file. These are measurements, not retried tests:

| Fixture location | Five synchronization durations, milliseconds |
| --- | --- |
| Checkout volume, under `target/test-artifacts/` | 1778.2975, 1898.8089, 3112.4861, 1944.3954, 1913.0325 |
| OS temporary directory | 2.0653, 2.0019, 1.9929, 2.0991, 2.1483 |

The diagnostic ran while the baseline release build was active. It demonstrates
the observed storage difference under build load, not a universal idle-device
latency guarantee. The subsequent full baseline run also overlapped focused
regression compilation in the separate fix target; the original focused
baseline preceded those other Cargo runs.

The old runtime synchronized every successful write and again on every close,
including read-only closes. The historical ten-small-files workload performs
20 synchronizations; five rapid write/read/close cycles perform 15; five
simultaneously open output files perform 10. Measured checkout synchronization
latency can therefore exceed the unchanged 5/8/10/30-second test limits even
for tiny files. This establishes storage-placement sensitivity and redundant
synchronization as contributing mechanisms; it does not identify the disk,
driver, antivirus, or other cause of the underlying volume latency.

Historical concurrent/performance failures are accounted for by that mechanism
and the existing fixture-isolation change, not relabeled as passing historical
runs. Every named concurrent/performance case now passes in the focused
current-main run. The error-suite failures remain reproduced on current main.

## Repair contracts

- Every test owns its temporary fixtures, including on assertion failure.
  Existing time limits remain unchanged. Error cases assert the catch branch
  and absence of unintended mutations; successful cases assert exact contents.
- Successful writes/appends retain their existing flush-and-sync step. Closing
  a clean or read-only handle avoids redundant synchronization. Creation or
  truncation without a subsequent successful write still requires close-time
  synchronization.
- Operations on one handle are serialized; an unrelated handle can progress
  while another operation waits. Close waits for an operation already using
  that handle, and later operations cannot write through a closed handle.
- Cancellation preserves state needed for cleanup. Tests use finite deadlines
  and real files; a test-only synchronization gate controls ordering without
  replacing disk writes, flushes, or synchronization.
- Closed text handles cannot fall back to filesystem paths and create `file1`.
  Aliases retain handle identity; ordinary literal and variable paths remain
  usable. Repeated close remains successful.
- The gated WFL flush program uses executable assertions and removes its
  output files in cleanup, rather than merely printing failure messages.

## Review-bot follow-up

The first automated reviews of `ea546187` identified two additional cases:

- [Devin review](https://github.com/WebFirstLanguage/wfl/pull/733#discussion_r4043520971):
  opening an existing file for append marked it dirty even if no write occurred,
  causing an unnecessary synchronization on close.
- [CodeRabbit review](https://github.com/WebFirstLanguage/wfl/pull/733#discussion_r4043532613):
  the error-suite permission guard used `expect` in `Drop`, so a cleanup error
  during an existing panic could abort the test process and hide its first
  failure. The equivalent CLI guard already used best-effort restoration.

These findings retain the existing R3 classification. The repair must preserve
append creation, existing contents, and symlink behavior without relying on a
separate existence check. Permission cleanup must restore an existing fixture
normally while tolerating an already removed fixture.

Test-only revision **`3540f0f5`** retains both reproductions before their fixes:

- `cargo test --lib interpreter::file_io_tests -- --nocapture`:
  **19 passed, 1 failed**. Opening and closing untouched empty and nonempty
  append targets produced two close-time sync events; neither was expected.
- `cargo test --test file_io_error_handling_test permission_restore_cleanup_
  -- --nocapture`: **1 passed, 1 failed**. Real permission restoration passed,
  while dropping the guard after removing its fixture panicked on `NotFound`.
  `catch_unwind` contained this reproduction without aborting the test runner.

The append repair first opens without allowing creation. Success is clean;
only `NotFound` uses the original create-enabled append operation. That fallback
is conservatively dirty, including when another process creates the file in
between the two opens. This bounds the work to two opens, preserves dangling
symlink behavior, and never infers dirtiness from a separate existence check.
The additional Unix symlink cases are platform coverage for Linux CI, not
locally executed Windows evidence.

Follow-up focused Windows Green: **22 lifecycle tests, 7 existing read/budget
tests, 13 error-suite tests, and 17 real CLI tests passed**. Additional
characterization gates the actual gap between the two opens to verify that a
competing creator's bytes survive and that cancellation before creation leaves
no file or registered handle. A caught sentinel panic verifies that permission
cleanup preserves the original panic payload. Formatting and independent
read-only review passed; review found no remaining actionable defect. Logs are
`append-open-green.log`, `append-open-budget-green.log`, and
`permissions-cleanup-review-green.log` under the existing raw-report directory.
The PR records final broad gates for the follow-up commit separately from the
earlier complete validation of `ea546187`.

CodeRabbit also reported a warning for documentation of touched functions.
The follow-up documents helper contracts, cancellation state, and cleanup
invariants. Its exact docstring percentage cannot be inferred locally from the
bot's summary; no percentage improvement is claimed without a new bot result.

## Limits and recovery

No file-format migration or configuration change is required. Reverting the
repair restores the prior implementation but also restores the reported
defects. Ordinary in-flight filesystem writes are not transactional; cancelling
a write does not promise to undo bytes already accepted by the OS. Physical
disk-full injection and power-loss durability are not claimed by these tests.
Network disconnect/backpressure gates are covered by the unchanged web suites;
this repair adds no network transport, channel, or configured resource limit.
Coverage percentages are not currently measured by the repository gate.
